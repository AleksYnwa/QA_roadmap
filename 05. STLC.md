#### Что такое STLC, какие основные этапы?

Жизненный цикл тестирования ПО (Software Testing Life Cycle) – это процесс тестирования программного обеспечения, который состоит из последовательных этапов, обеспечивающих качество продукта.

1. **Анализ требований** – что тестировать.
2. **Планирование** – стратегия, инструменты, сроки.
3. **Разработка чек-листов/тест-кейсов** – создание сценариев проверки.
4. **Подготовка тестовой среды** - настройка окружения.
5. **Выполнение тестов** – запуск, баг-фиксация.
6. **Завершение** – отчёт, выводы о качестве
#### 7 основных принципов тестирования

1. **Тестирование показывает дефекты** – но не гарантирует их полного отсутствия.
2. **Исчерпывающее тестирование невозможно** – нельзя проверить все комбинации данных.
3. **Раннее тестирование** – чем раньше начать, тем дешевле исправлять ошибки.
4. **Скопление дефектов** – большинство багов сконцентрировано в нескольких модулях.
5. **Парадокс пестицида** – одни и те же тесты со временем перестают находить новые дефекты.
6. **Тестирование зависит от контекста** – подходы различаются (например, банк vs. сайт-визитка).
7. **Заблуждение об отсутствии ошибок** – даже если багов нет, система может быть неудобной для пользователя.

#### Что такое требования и какие атрибуты должны быть у требований?

**Требования** – это четкое описание того, что система должна делать, какими свойствами обладать и каким условиям соответствовать.

Качественное требование должно обладать следующими характеристиками:

1. **Корректность** – точно отражает потребности заказчика.
2. **Однозначность** – исключает двусмысленности (например, "быстро" → "реакция < 2 сек").
3. **Полнота** – содержит все необходимые детали (входы, выходы, условия).
4. **Непротиворечивость** – не конфликтует с другими требованиями.
5. **Проверяемость** – можно объективно проверить (тестами, анализом).
6. **Атомарность** – описывает одну функциональность (не объединяет несколько).
7. **Актуальность** – соответствует текущим нуждам бизнеса/пользователей.
8. **Трассируемость** – имеет связь с другими артефактами (тест-кейсами, задачами).
9. **Реализуемость** – технически и экономически выполнимо.

#### Метрики тестирования

1. **Passed/Failed Test Cases**. Используется для оценки отношения удачно пройденных тестов к завершившимся с ошибками.
2. **Not Run Test Cases.** Демонстрирует количество тестов, которые нужно выполнить для данного проекта.
3. **Open/Closed Bugs**. Формируется из отношения открытых багов к закрытым.
4. **Reopened/Closed Bugs**. Рассчитывает соотношение переоткрытых багов к закрытым
5. **Bugs by Severity/Priority**. Общее количество багов по серьёзности/приоритету.

Метрики можно добавлять до бесконечности, но одну из интересных можно добавить - количество багов в "проде".

#### Для чего нужны метрики тестирования?

1. Улучшение / оптимизация процессов / результата, если грамотно подбирать, интерпретировать и влиять на метрики.
2. Контроль процесса тетсирования.
3. Оценить качество продукта (понять, насколько ПО соответствует требованиям; выявить «слабые» места (модули с наибольшим количеством дефектов))
4. Принимать обоснованные решения (решить, готов ли продукт к выпуску (на основе данных, а не интуиции); доказать необходимость доработок заказчику или руководству)
